Today we're walking through two planning documents, both written for the SilverBullet M3e project. That's a fork of SilverBullet — the self-hosted notes wiki — being reskinned with the Material 3 Expressive web-component library. One document is a shovel-ready user-interface redesign. The other is research for a journal-driven synthesis engine. Let's take them in order.

First, some context on where things stood. The app had just merged a big redesign: a horizontal navigation bar across the bottom, with five destinations, a floating action button for adding content, and slide-up panels for each destination. That work was done and merged. And then the direction changed.

So, spec one: go back to a vertical toolbar. Instead of a horizontal bar, a slim toolbar pinned to the bottom-right corner. It carries four buttons — Search, Navigation, Journal, and Notifications. The read-only toggle stays up in the top-right of the app bar. And the whole "add item" pattern, including the floating action button, gets retired. From now on, new content comes in through journaling alone. Hold that thought, because spec two is what makes journaling powerful.

Now, the search button. It opens a sheet that slides up from the bottom, with a search bar at the top. On the left of that bar is an icon. Tap it, and a menu lets you switch modes. Search mode looks through all the text. Open mode looks for file names. Run mode looks for commands. And below the bar, a live list of recent searches updates as you type. The key rule here: no dropdown lists. The results live right inside the sheet. That matters, because earlier attempts at search had been rough, and dropdowns were the culprit. So the plan bakes in a screenshot test with specific checks.

The navigation button opens its own sheet, this one with tabs: History, for pages you've visited; Changelog, for what changed and when and by whom; and Sitemap, for all your files. Journal and Notifications are just quick links to today's pages.

Here's the interesting part — what the planning agent found once it actually read the code. Four things flipped. One: the read-only toggle currently has no home at all. It's a live bug, left over from deleting the old toolbar too early. The plan puts it back. Two: recent-search history was assumed to need building, but it already exists. Free win. Three: the "commonly navigated" sitemap feature is nearly free, because the data's already tracked. And four: the one genuinely hard piece is showing who changed a page. There's no way to get author information on the server side today. The "when" is easy; the "who" needs new work, or it waits. There was also a small landmine — one of the menu components doesn't emit the event the mode-switcher would rely on, so that needs verifying before it's wired. All told, the UI plan is ten steps.

Now, spec two. This one's more ambitious. The idea: journal freely, in one place. When you mark an entry done, a language-model agent reads it and routes the pieces where they belong. A contact goes to your contacts. An event goes to your calendar. A to-do goes to your to-do list. When it finishes, you get a push notification, and a summary lands in the day's notifications page. The model gateway is LiteLLM.

And here's the headline finding. This isn't starting from scratch. The research turned up an existing pipeline, already merged, with thirty-five tests, that already does the whole chain — watch, classify, route, write back, and notify. The notification piece is already wired. So the parts people assumed were the hard build are largely done.

What's actually missing is narrower. The current trigger runs continuously, instead of waiting for a marker. It uses a local model instead of LiteLLM with tool-calling. And there's no debounced backup-commit, and no file watcher on the host.

So the recommendation is an external file-watcher daemon running on the SilverBullet host. One idle pass, after changes settle for a few minutes, does two jobs at once: it commits your changes to a backup repo, and it scans for the synthesis marker. It reuses everything the existing pipeline already does, and swaps in just two things — the trigger gate and the model backend.

Two clever details worth calling out. The marker isn't the existing "done" tag — it's a dedicated tag, so it doesn't overload something that already means something else. And when the marker's been handled, the system records that in a separate ledger file, rather than editing the page to remove the marker. Why? Because editing the page is itself a change, and that change would race the very timer that's watching for changes. Subtle, but it'd cause re-triggering bugs. And one hard constraint fell out of the research: SilverBullet itself can't be the trigger host. Its only save-hook fires from the browser tab, and does nothing for writes that come in over the API. So the watcher has to live outside.

To wrap up. Both efforts now have documents. The toolbar redesign is ready to build. The synthesis engine is waiting on a green-light before its build plan gets written. Two small decisions are still open on the interface side: where the push-notification toggle lives, and whether to build author-tracking now or defer it. And a bit of cleanup happened along the way — a stale branch from the abandoned nav-bar work was discarded cleanly, with nothing lost. That's the state of both specs.
