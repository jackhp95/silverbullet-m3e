## 3. Two paths, estimated

### Path (a): Reimplement the picker/command-palette customizations against main's navigator/panel API

What's actually needed: main's `client/navigator/` is a real, already-built declarative view system (registry + per-view hooks `meta/rows/content/select/create/key/action/rowState/dropdown/move`, docks incl. `modal`, built-in views `std.pages`/`std.anchors`/`std.tags`). It is **more capable** than the old AnythingPicker, and it already covers the anchor-picking use case `useAnchorOptions` hard-coded. The remaining work is UI-layer, not logic-layer:
- Re-skin/re-host `search_sheet.tsx`'s M3E chrome (bottom-sheet, mode menu, search-bar) as a renderer plugged into the navigator's `modal` dock instead of its own bespoke fetch/filter/anchor logic.
- Same for `navigation_sheet.tsx` (History/Changelog/Sitemap) — these are less coupled to the deleted files and may need little more than a wiring change (they don't import from anything_picker/command_palette at all per the import grep).
- Rewire `editor_ui.tsx`'s FAB/toolbar to open navigator docks instead of `showCommandPalette`/`AnythingPicker` state.
- Drop `anything_picker.tsx`/`command_palette.tsx` entirely (they're gone on main anyway) and delete/rewrite `useAnchorOptions` in favor of `std.anchors`.

**Effort:** medium — one focused engineering slice (est. 2-4 days), because the target API already exists and is well-formed; this is porting a UI onto a superset API, not designing a new one. **Risk:** medium — must learn an undocumented-outside-code 75-file subsystem correctly, and get the modal-dock UX to actually match Stream A's bottom-sheet interaction model (main's navigator API doesn't obviously have "bottom sheet with detents" — may need new dock-rendering work on main's side too, which is riskier since it touches main's own architecture, not just m3e-fork's UI layer).

**Recommendation: this path.** It preserves main's 255 commits of architecture (live collab, sync engine, revision history, Git status — all real, valuable, unrelated work Jack doesn't want to lose or fight) and produces a genuinely reconciled codebase instead of a fork that drifts further every time main ships. The alternative (b) below doesn't actually solve the problem, it just defers it.

### Path (b): Commit-by-commit rebase of m3e-fork onto main

124 commits × conflict resolution, where ~20-25 of them touch the 30 conflicted files above (most commits are single-slice and additive, so the conflict-bearing subset is a minority, but it's the *architecturally hard* minority — the exact ones needing path-(a)-style design work anyway). Rebasing does not avoid the reimplementation; it just interleaves it with 100+ mechanical rebase-conflict resolutions across 124 commits, most of which touch files that already cherry-pick clean and gain nothing from being replayed one commit at a time.

**Effort:** high (est. 1.5-2x path (a), because you still do the navigator-API redesign, plus pay a large tax replaying non-conflicting commits one-by-one and re-resolving the *same* conflict repeatedly as it recurs across the sequential commits that touch `editor_ui.tsx`/`top_bar.tsx`/etc.). **Risk:** high — 124 individual conflict-resolution steps is a lot of surface for a silent semantic regression to hide in, and it produces a messy history that still needs the same design decision (path a) made partway through, under worse conditions (mid-rebase, one commit's diff at a time, less context).

**Recommendation: reject.** Not because it's unsafe, but because it does strictly more work than (a) for the same end state, and buries the one genuinely hard decision (how to re-host the picker UX) inside a mechanical process instead of surfacing it as its own reviewable unit.
